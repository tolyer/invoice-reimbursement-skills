| 滴滴用车 | 滴滴出行行程报销单 | 滴滴电子发票 + 支付截图（**须含高速费明细**） | 中行牌价截图（CNY） |

## 二、勾稽核对关系

1. **飞机行**：订单总额（确认邮件/订单详情） = 机票价 + 附加服务费 = 支付截图金额（首次扣款）；**若订单有退款，则实报金额 = 订单总额 − 已退款金额 = 行程单票价合计**，三方必须对齐（见第 6 条）。
2. **酒店行**：水单金额 = 支付截图金额；入住证明尾号 = 水单订单尾号；多段连住每段独立一行；**有退款时同样取退款后净额**。
3. **携程用车（专车）行**：用车行程单金额 = 用车电子发票「价税合计」 = 支付截图金额，三者一致。注意携程用车发票可能是「差额征税-差额开票」，此时发票的**金额列 ≠ 价税合计**，一律以**价税合计**（大写小写并列那行）为准。
4. **专车与飞机是否合并**：**以支付凭证勾稽结果判定，不得默认合并**（2026-09-06 修订）。
   设 机票订单金额 = A、专车行程单金额 = B、支付截图金额 = C：

   | 勾稽结果 | 说明 | 处理 |
   |---|---|---|
   | **C = A + B** | 一笔支付同时覆盖机票与专车 → **同一个携程订单** | **合并成一行**：金额 = A + B；票据本体 = 机票订单确认邮件；专车行程单列入附件；备注注明「含 MMDD 携程专车送机」 |
   | **C = A**（专车另有独立支付），或 **C = B** | 两笔支付分开 → **两个独立携程订单** | **分别成行**：飞机行、专车行各自独立；专车行票据本体 = 用车行程单，两行各配自己的支付截图 |

   - 出现多张支付截图时，先按《文件识别规则》的「作废凭证判定」确定有效凭证，再做上述比对。
   - 判定结论与勾稽算式必须写进台账，并请用户确认后才归档。
   - 多趟专车时：**先各自与自己的支付截图配对**，再决定合并/独立；同一行程内多趟专车是并成一行还是逐趟成行，**须询问用户**。
5. **滴滴用车行**：**行程单金额 + 高速路桥费 = 支付金额 = 实报金额**（三者必须相等）。
   - 滴滴「出行行程报销单」的「金额」列**不含高速费**；高速费在「费用说明」页单独列出（列名类似「高速路桥费(全额给司机 不参与优惠)」）——**必须把费用说明页也取到**，否则金额会少算。
   - 实报金额取**含高速费的支付金额**，不是行程单的金额列。
   - ⚠️ **滴滴电子发票的「价税合计」= 行程单金额，仍不含高速费**（2026-10-04 验证：发票 57.50 = 行程单 57.50，支付 66.50）。高速费**无票**，凭费用说明页佐证并入本行金额。**禁止**因「发票只开到 57.50」就把实报金额写成 57.50。
   - 勾稽算式必须写进备注：如「行程单57.5+高速费9=66.5」。
6. **退款核验（携程类通用）**：见第六节「退款处理」。
6-补. **改签核验（携程机票）**：见第七节「改签处理」。核心：**实报依据 = 改签发票 TOTAL / 订单详情页总计**（含改签手续费），**不是**改签后行程单的金额（少一张 CHANGEFEE）。
7. **Grab**：逐笔加总必须 = 对账单合计（±0.01）；剔除私人行程后得到报销小计；对账单可直接作票据本体。
8. **补助**：**按工作日计**，天数算法见第四节（出发日 0.5 + 中间工作日 + 返回日 0.5，周末剔除，节假日不自动扣但须提醒用户确认）；金额 = 天数 × 日标准（当前 75 USD/天）。

## 三、Grab 私人行程判定（须用户确认）

疑似私人行程特征：
- 路线非「住所 ↔ 职场」通勤（如去车站、商场、景点）；
- 异常时段（深夜、周末非加班日）；
- 用户事先声明的私人安排。

处理：**列出疑似条目 → 询问用户 → 确认后在台账标「否/私人行程，未计入报销」**，并在 Grab 行备注中写明「其中MMDD XX行程 NN.NN 为私人行程，未计入」。

## 四、补助天数算法（只看工作日）

> 2026-09-06 修订：周末不计入；节假日不自动扣减，但须在台账提醒用户二次确认。
> 配套文件：`references/节假日日历.md`（放假安排，每年 11 月更新）
> 配套工具：`scripts/calc_subsidy.py`（可直接跑，输出逐日明细与节假日提醒）

### 1. 逐日规则

| 日期 | 名义天数 | 是否计入 |
|---|---|---|
| 出发日 | 0.5 | 逢工作日计入；**逢周末计 0**（见开关 S2） |
| 中间日 | 1.0 | 仅**工作日**计入，周末计 0 |
| 返回日 | 0.5 | 同出发日 |

- 出发日 = 返回日（当日往返）时，合计 1.0 天。
- **调休上班日**（日历里标 `workday` 的周末）按工作日计入。
- 计算必须**逐日展开**，不能拿「总天数 − 估算周末数」估算——跨周时极易算错。

### 2. 可调开关（改这里就生效）

| 开关 | 默认 | 含义 |
|---|---|---|
| `DEDUCT_HOLIDAY` | `false` | `false` = 节假日不扣天数，只提醒确认；公司明确不发时改 `true` 自动扣除 |
| `WEEKEND_TRAVEL_DAY` | `false` | `false` = 出发/落地日逢周末计 0；若公司政策允许 travel day 计半天，改 `true` |

对应脚本参数：`--deduct-holiday`、`--weekend-travel-day`。

### 3. 节假日提醒（必做）

算出天数后，拿 `references/节假日日历.md` 比对出差区间：

- 区间**跨越**法定节假日 → 补助行打 **⚠️** 并列出具体日期与节日名，**请用户二次确认**是否计入；台账里要写明「区间含 XX 节日 X 天，当前未扣除，待确认」。
- 区间**不含**节假日 → 台账注明「区间内无法定节假日」即可。

> 提醒必须落在**输出的表格里**（补助行备注或单独一行提示），不能只在对话里说一句。

### 4. 算例（0720-0806 吉隆坡）

```
python3 scripts/calc_subsidy.py 2026-07-20 2026-08-06 --rate 75 --fx 7.84
→ 计入 13.0 天 = USD 975.00 = HKD 7,644.00
  （旧口径含周末为 17 天 / USD 1,275.00，差 4 天，来自 07-25、07-26、08-01、08-02 两个周末）
```

### 5. 周末 / 节假日加班确认（2026-10-04 新增，硬性）

> **规则**：凡是出差区间内的**周末**或**法定节假日**，都必须**主动提醒用户确认当天是否正常加班**；
> **用户回答「是（加班）」→ 当天照计补助**；但若当天恰为**出发日或到达日，仍只记 0.5 天**（半天规则优先级更高）。

| 场景 | 默认算法 | 用户答「加班」后 |
|---|---|---|
| 周末（中间日） | 0 天 | **1.0 天** |
| 周末（出发日 / 到达日） | 0 天 | **0.5 天** |
| 法定节假日（中间日） | 不扣，1.0 天 | 1.0 天（不变，但要标注「节假日加班」） |
| 法定节假日（出发日 / 到达日） | 不扣，0.5 天 | **0.5 天**（不变） |
| 调休上班日（日历标 `workday` 的周末） | 按工作日计 | 标注「调休上班」，无需再问加班 |

**执行要求**

1. 输出补助逐日台账时，周末 / 节假日行的「是否加班」列一律先写 **待确认**；
2. 在台账表格内（不是只写在对话里）列出**具体哪几天需要确认**；
3. 用户逐天答复后重算并更新台账与 txt；**不得默认「周末没加班」直接定稿**。

### 6. 补助逐日台账 txt（必须生成并归档为附件）

> 补助行无票据本体，稽核时全靠这份逐日明细佐证天数，因此 **txt 必须作为补助行附件之一上传用友平台**。

**格式要求**：每天一行，列固定为
`日期 ｜ 星期几 ｜ 假期/调休（含节日名，如「中秋节」）｜ 是否加班 ｜ 补助天数（0.5 / 1）｜ 说明`

```
日期        星期   假期/调休             是否加班          补助天数  说明
2026-09-20  周日   国庆调休上班日        是（调休上班）    0.5       出差出发日（深圳→吉隆坡）
2026-09-25  周五   中秋节（放假第1天）   待确认            1.0       节假日默认不扣（已确认）
2026-09-26  周六   中秋节假期            待确认            0.0       周末，默认剔除
合计                                                       8.0 天    × 75 USD/天 = USD 600.00
```

- 文件命名：`02-补助逐日台账-<区间>.txt`，放在补助行 `☆附件/` 下，位于汇率截图之后；
- 尾部附「待确认」清单（哪几天需确认是否加班）；
- 中文列宽按**显示宽度**对齐（汉字算 2 宽），否则终端/记事本里会参差不齐。

## 五、汇率与折算口径

| 币种 | 汇率来源 | 折算方向 | 示例 |
|---|---|---|---|
| CNY | 中行外汇牌价（港币折算价） | 原币 ÷ 折算价小数 = HKD | 2,484 ÷ 0.8646 = 2,873.00 |
| MYR | Google 汇率 | 原币 × 汇率 = HKD | 595.34 × 1.93 = 1,149.01 |
| USD | Google 汇率 | 原币 × 汇率 = HKD | 1,275 × 7.84 = 9,996.00 |

- 汇率取值日：通常为提交前一两天，截图文件名须记录在台账「汇率依据」中。
- **汇率映射强制确认**：每张汇率截图必须逐张视觉读取（**不看文件名**），在台账中列出「文件名 ↔ 币种对 ↔ 数值 ↔ 来源」映射表并请用户确认；`SCR-` 之类前缀只是本机截图工具的默认命名，**不是汇率截图的判断条件**，任何文件名不含币种信息，不得凭假设归类（教训：2026-09-05 skfe/sjyj 互换事件）。
- ⚠️ **核对报价方向**（2026-10-04 新增）：截图可能写成「1 HKD = X 外币」而非「1 外币 = X HKD」。若方向相反，取倒数换算（`1 USD = 1 ÷ 0.1274 ≈ 7.85 HKD`）；页面大字为四舍五入值时，改读走势图末点并用刻度线性映射取到 0.0001 精度。
- ⚠️ **反算结果必须二次确认**（2026-10-04 修订，硬性）：**反算逻辑保留可用，但反算值一律不得直接用于折算与归档**。必须——① 在台账汇率映射表中列出「截图原文 + 完整换算过程」；② **明确请用户确认该反算值，或请用户补充一张直接报价（1 外币 = X HKD）的截图**；③ 用户书面确认后方可折算。宁可多问一轮，不得默认采用。
  - 正面案例：2026-10-04 补助行 USD 汇率，先用反算得 7.8472 → 用户随即补来直接报价截图「1 USD = 7.85 HKD」，两者一致，反算得到验证；反之若无直接报价，**必须停下来问**。
- 报销货币一律 **HKD**；报销单计价货币为 USD（平台设置，不影响逐行折算）。
- 报销金额保留两位小数，四舍五入。

## 六、退款处理（携程类通用）

> 2026-10-04 新增。适用于机票、酒店、用车等所有携程订单。

### 1. 核心口径

**实际报销金额以「退款后金额」为准，不是以支付金额为准。**

```
实报金额 = 订单总额 − 已退款金额
```

### 2. 三个金额的区分（容易混）

| 金额 | 出处 | 用途 |
|---|---|---|
| **支付金额** | 银行/银联交易详情截图（首次扣款） | **仅作附件佐证**，不等于报销金额 |
| **订单总额** | 携程订单确认单 / 订单详情页「总计」 | 用于计算退款后净额 |
| **已退款金额** | 携程订单详情页「已退款 ¥XXX」 | 从订单总额中扣减 |
| **实报金额** | = 订单总额 − 已退款 | **进报销单的数值**，且应 = 行程单票价合计 |

### 3. 勾稽链（三者必须收敛到同一个数）

```
支付截图金额 − 已退款金额 = 行程单金额 = 实报金额
        3,748.00 − 177.00 = 3,571.00 = 3,571.00   ✓
```

任一项对不上 → 列为勾稽不符，**先查清再出账**（常见原因：部分退票、退改签手续费、优惠券抵扣未体现在行程单）。

### 4. 台账要求

- 台账必须**并列三列**：`支付金额 / 退款金额 / 实报金额`，不能只写一个数。
- 退款凭证（订单详情页含「已退款」的截图、退款到账记录）**必须归档为附件**；若订单详情页同时充当票据本体，需在台账中说明「同文件双用」。
- 备注写明算式：如「订单总额3748-已退款177=3571」。

### 5. 待确认项

- 若退款原因涉及**退改签手续费**（手续费是否可报销），金额与政策不明时**必须询问用户**，不得自行判断。
- 若行程单金额与「订单总额 − 已退款」不一致，说明可能存在未落地的退款，一律停下来问。

## 七、改签处理（携程机票）

> 2026-10-04 新增。脱敏案例：订单 ORDER-EXAMPLE（深圳航空 ZH327 / ZH330，04-27 深圳→吉隆坡、05-04 吉隆坡→深圳；返程由 05-14 **改签提前**至 05-04）。

### 1. 核心口径

**改签订单实报金额 = 改签发票 TOTAL（= 携程订单详情页「总计」）**：

```
实报金额(整单) = FARE 机票款 + TAX 税费 + CHANGEFEE 改签手续费 + PRICE DIFFERENCE 差价 + Tax Difference 税差
              = 原票款支付 + 改签费支付
```

⚠️ **改签后行程单的「总计」不含 CHANGEFEE**（改签手续费），只作附件佐证，**不得作报销依据**。
⚠️ 与退款方向相反：**退款取净额（支付 − 退款），改签取总额（原票款 + 改签费）**。

### 2. 报销范围（必须先问用户）

| 方案 | 金额 | 适用前提 |
|---|---|---|
| **整单** | FARE + TAX + CHANGEFEE + PRICE DIFFERENCE = 发票 TOTAL | 该订单**未在其他批次报过** |
| **仅改签新增** | CHANGEFEE + PRICE DIFFERENCE = 改签费那笔支付金额 | 原票款（FARE + TAX）**已在其他批次报过** |

案例：整单 **5,216.00**；仅改签新增 **1,040.00**（450 手续费 + 590 差价）。

### 3. 勾稽链（全部要跑，任一不成立即列为勾稽不符）

```
① 原票款支付 = FARE + TAX                     2,867.00 + 1,309.00 = 4,176.00 ✓
② 改签费支付 = CHANGEFEE + PRICE DIFFERENCE     450.00 +   590.00 = 1,040.00 ✓
③ 两笔合计   = 发票 TOTAL = 订单详情页总计      4,176.00 + 1,040.00 = 5,216.00 ✓
④ 行程单票价 = FARE + PRICE DIFFERENCE          2,867.00 +   590.00 = 3,457.00 ✓
⑤ 行程单总计 = 行程单票价 + TAX                 3,457.00 + 1,309.00 = 4,766.00 ✓
⑥ 发票 TOTAL = 行程单总计 + CHANGEFEE           4,766.00 +   450.00 = 5,216.00 ✓
⑦ 改签明细   = 改期手续费 + 机票差价 + 税差      450.00 + 590.00 + 0.00 = 1,040.00 ✓
```

> 注：**发票 FARE（2,867）≠ 行程单票价（3,457）**，差额正是 PRICE DIFFERENCE（590），属正常，不是勾稽不符。

### 4. 台账要求

- 台账必须**并列两张总额**：`发票 TOTAL（实报依据）` 与 `行程单总计（仅佐证）`，并写明差额 = CHANGEFEE；
- 改签三项拆解（改期手续费 / 机票差价 / 税差）逐项列出；
- 归档：**改签发票 = 票据本体**；改签费用详情截图、新旧航班信息截图、改签后行程单、两笔支付截图、汇率截图进附件；
- 备注写明算术式，示例：
  `改签订单ORDER-EXAMPLE,原票款4176(机票款2867+税费1309)+改签费1040(手续费450+差价590)=5216,汇率为5216/0.8584=6076.42`

### 5. 待确认项

| 事项 | 说明 |
|---|---|
| 报销范围 | 整单 vs 仅改签新增，**必须问用户，不得自行假定** |
| 原票款是否已报过 | 决定能否只报改签费（1,040） |
| CHANGEFEE 是否全额可报 | 部分公司对改签手续费有限额或不予报销，政策不明时必须问 |

### 6. 改签 + 退款混合场景（2026-10-04 新增，重点）

同一张携程机票订单完全可能**既改签又退款**（先改签后退票/部分退，或反过来）。这是最容易出错的组合，原因有三：

- **支付截图只看得见扣款**，退款看不见；
- **改签发票是退款之前开的**，TOTAL 仍是全额，**不会因后续退款作废或降额**；
- **行程单**只显示票价 + 税费，**既不含改签手续费，也不反映退款**。

#### 6.1 统一公式（一行净额）

```
实报金额（净额） = 所有支付合计 − 已退款金额
                = (原票款支付 + 逐次改签支付) − 已退款
                = 订单详情页的「实付 / 已支付」金额（须与前两者一致）
```

| 情形 | 实报金额 |
|---|---|
| **只有改签，无退款** | = 发票 TOTAL = 支付合计（案例：5,216.00） |
| **改签 + 退款** | = 发票 TOTAL **− 已退款**（⚠️ **不等于**发票 TOTAL） |
| **只有退款，无改签** | = 订单总额 − 已退款（走第六节口径） |

#### 6.2 ⚠️ 改签手续费原则上不退

改签费用详情页通常明写「**改期后再退票此费用不退还**」。因此：

- 退款一般只冲减**票款 / 税费**部分，`CHANGEFEE` 通常仍由用户承担；
- 若订单详情页的退款金额看起来把改签费也退了（属特殊处理），**必须在台账标 ⚠️ 并请用户确认**，不得照搬；
- 退票若另产生**退票手续费**，作为减项并入本行同一个净额里，同样不单独成行。

#### 6.3 混合场景勾稽链

```
① 支付逐笔：原票款 4,176.00 + 改签费 1,040.00 = 5,216.00
② 退款：订单详情页「已退款 X」
③ 净额：5,216.00 − X = 实报金额      ← 报销单「含税金额」填它
④ 交叉验证：订单详情页「实付 / 已支付」金额 = ③
   └─ 对不上 = 勾稽不符，停下来问用户，不得自行调平
```

#### 6.4 同一订单一行（预览表不拆行）

| 做法 | 判定 | 正确处理 |
|---|---|---|
| 机票一行 + 改签费另起一行 | ❌ 拆行 | 同一 ORDER ID **只出一行** |
| 退款做成负数行 | ❌ | 在本行内减掉，只体现净额 |
| 多次改签拆成多行 | ❌ | 同一行累加，备注里逐次写清（`-n0501改签1040-`） |

> 与专车「C = A + B 合并成一行」是同一个思路：**能由一个订单号统起来的费用，就进同一条记录。**

#### 6.5 必取材料（缺哪样就主动向用户要，不等他问）

| 必取材料 | 缺了会怎样 |
|---|---|
| **订单详情页**（退款只在这里露出） | **有退款却不知道 → 直接多报** |
| 改签发票（PAYMENT DETAILS 六项） | 拆不出 CHANGEFEE / PRICE DIFFERENCE |
| 「核对改签费用」详情截图 | 无法验证改签支付金额 |
| 改签信息截图（新航班 vs 原航班） | 无从确认改签方向、行程单是否已更新 |
| 逐笔支付截图（原票款 + 每次改签一张） | 做不了「支付合计 = 发票 TOTAL」勾稽 |
| 改签后行程单 | 缺最终票价 / 税费佐证 |
| 退款到账记录（银行卡/支付宝入账） | 只有 App 页面、查不到实际到账金额时，用它验证 X |

#### 6.6 备注模板（混合场景）

```
改签订单<订单号>,原票款4176(机票款2867+税费1309)+改签费1040(手续费450+差价590)=5216,后退款X,实报5216-X=Y,汇率为Y/0.8584=Z
```

> 退款出现在曾在文件夹里但还没被认领的截图上时（例如一张「已退款」的银行入账通知），同样要进记账、进附件，不能忽视。
