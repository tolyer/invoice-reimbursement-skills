## v1.8.0 · 2026-10-04

**变更类型**：次版本号（改签能力深化：**混合场景 + 一行合并 + 缺料主动索要**）

> 用户反馈：识别准确；要求覆盖「**携程订单同时存在改签 + 退款**」的场景，后续遇到这类材料要**主动识别并提醒补充**，且**报销单预览表内统一合并成一行**。

**① 新增「同一订单 = 一行」硬性规则**

> 一个携程 `ORDER ID` 只占一行报销记录：票款 + 改签手续费 + 机票差价 + 税费 + 燃油 + **退款冲减**全部并入同一行的**净额**。
> - **退款不做负数行**，在本行内减掉；
> - **多次改签只累加、不拆行**，备注里逐次写清算式；
> - 票据本体：**有退款**→优先订单详情页（同时露出应付与已退款）；**无退款**→改签发票；其余全进附件。
> - 思路与既有的「专车 C = A + B 合并一行」一致。
> - 位置：`SKILL.md` 第 2 步 + 硬性原则、`报销单填写逻辑.md` 新增「二·补、同一订单 = 一行」（含三种备注模板）、`README.md` 3.8 + 九件事第 9 条。

**② 新增「改签 + 退款混合场景」处理（重点）**

> 最容易多报的组合，原因有三：**支付截图看不见退款**、**改签发票是退款前开的（TOTAL 仍为全额，不因退款作废）**、**行程单既不含改签费也不反映退款**。
>
> **统一公式**：`实报金额 = 所有支付合计（原票款 + 逐次改签）− 已退款 − 退票手续费`，且须等于订单详情页的「实付 / 已支付」金额，对不上就是勾稽不符，须停下来问。
>
> ⚠️ **改签手续费原则上不退**（携程原话「改期后再退票此费用不退还」）：退款多半只冲减票款部分；若看起来连手续费也退了，须标 ⚠️ 请用户确认，不得照搬。退票产生的手续费同样并入本行减项。
>
> 位置：`账单分类与勾稽规则.md` 第七节新增第 6 小节（公式表、混合勾稽链、一行合并对照、必取材料、备注模板）、`文件识别规则.md` 1-A 末尾「改签 + 退款同时出现时怎么认」查核表、README 3.8。

**③ 新增「缺料必须主动索要」规则**

> 识别出改签订单后逐项比对必给清单，**缺哪样当场开口要，不等用户追问**：① 订单详情页（**退款只在这露出，漏了必多报**）② 改签发票六项拆解 ③ 改签费用详情截图 ④ 新旧航班对照 ⑤ 逐笔支付截图（原票款 + 每次改签各一张）⑥ 改签后行程单 ⑦ 退款到账记录（仅有 App 页面时用它验证）。
>
> 位置：`SKILL.md` 第 2 步（含对照表）+ 硬性原则、`账单分类与勾稽规则.md` 第七节 6.5。

**④ 其他**：`SKILL.md` 受理范围第 2 条描述补充「含改签+退款混合、同一订单只出一行、主动索要缺料」。

## v1.7.0 · 2026-10-04

**变更类型**：次版本号（新增第 7 类凭证「携程机票改签」+ 新增勾稽规则第七节）

**① 受理范围 6 类 → 7 类**，新增「**携程机票改签**」（位列第 2，紧跟携程飞机票）。

**② 新增《账单分类与勾稽规则》第七节「改签处理（携程机票）」**

> - **核心口径**：改签订单实报金额 = **改签发票 TOTAL（= 订单详情页总计）** = `FARE + TAX + CHANGEFEE + PRICE DIFFERENCE + Tax Difference` = `原票款支付 + 改签费支付`。
> - **最大陷阱**：改签后**行程单的总计不含 CHANGEFEE（改签手续费）**，比发票少一笔（案例：发票 5,216.00 vs 行程单 4,766.00，差 450.00）——只看行程单会**少报 450 元**。
> - **方向相反提醒**：**退款取净额**（支付 − 退款），**改签取总额**（原票款 + 改签费），两者可能同时出现在一张订单上。
> - **7 条勾稽链**：① 原票款支付 = FARE + TAX；② 改签支付 = CHANGEFEE + PRICE DIFFERENCE；③ 两笔合计 = 发票 TOTAL = 订单详情总计；④ 行程单票价 = FARE + PRICE DIFFERENCE；⑤ 行程单总计 = 行程单票价 + TAX；⑥ 发票 TOTAL = 行程单总计 + CHANGEFEE；⑦ 改签明细 = 手续费 + 差价 + 税差。
> - **报销范围必须先问用户**：整单（含原票款）vs 仅改签新增（CHANGEFEE + PRICE DIFFERENCE，前提是原票款已报过）。
> - 注：**发票 FARE ≠ 行程单票价**（差额 = PRICE DIFFERENCE），属正常，不是勾稽不符。

**③《文件识别规则》新增「1-A 携程机票改签」小节**

> 识别 5 类文件：改签发票（文件名可能叫「机票改签单」，内容实为 Trip.com `ITINERARY/INVOICE`，第 2 页有携程香港财务部章）、改签费用详情截图（改期手续费/机票差价/税差）、改签信息截图（新旧航班对照）、改签后行程单、两笔支付截图。识别技巧新增第 11~13 条（改签单文件名陷阱、新旧航班对照、` (1)` 后缀跨目录不误判）。

**④《报销单填写逻辑》新增改签行**

> 票据本体 = 改签发票；金额字段填发票 TOTAL；附件固定五件以上；备注模板两套（整单 / 仅改签新增）。

**⑤ 同步**：`SKILL.md` 受理范围与第 2 步核验要点、硬性原则新增「改签取总额、退款取净额」；本 CHANGELOG。

## 版本号怎么定

| 变更类型 | 改动哪一位 | 例子 |
|---|---|---|
| 文案修订、错别字、表格格式、局部纠错 | **修订号**（1.2.0 → 1.2.1） | 修正某个汇率数值笔误 |
| 新增规则条目、新增文件（如新的 README）、补充判定分支 | **次版本号**（1.2.0 → 1.3.0） | 新增一种凭证类型、新增 README |
| 工作流结构性调整、步骤增删、归档方式变化 | **主版本号**（1.2.0 → 2.0.0） | 把「确认后才归档」改成「边核验边归档」 |

> 每次改动请同步：① 本文件新增一条；② `SKILL.md` frontmatter 的 `version` 字段；③ 被改动的 `references/*.md` 顶部「最近更新」日期。

## v1.6.0 · 2026-10-04

**变更类型**：次版本号（补助规则新增判定分支 + 新增归档产出物）

**① 新增「周末 / 节假日是否加班」确认规则（硬性）**

> 出差区间内的**每一个周末日和法定节假日**，都必须主动提醒用户确认当天是否正常加班。
> **用户答「是（加班）」→ 当天照计补助**；但若当天恰为**出发日或到达日，仍只记 0.5 天**（半天规则优先级更高）。

| 场景 | 默认算法 | 答「加班」后 |
|---|---|---|
| 周末（中间日） | 0 天 | **1.0 天** |
| 周末（出发日 / 到达日） | 0 天 | **0.5 天** |
| 法定节假日（中间日） | 不扣，1.0 天 | 1.0 天（标注「节假日加班」） |
| 法定节假日（出发日 / 到达日） | 不扣，0.5 天 | 0.5 天（不变） |
| 调休上班日（日历标 `workday`） | 按工作日计 | 标注「调休上班」，无需再问 |

执行要求：周末 / 节假日行的「是否加班」列**先写「待确认」**，并在**台账表格内**（不是只写在对话里）列出具体待确认日期；**不得默认「周末没加班」直接定稿**。

**② 补助逐日台账 txt 必须生成并归档为附件**

补助行无票据本体，稽核看的就是天数怎么来的，因此逐日明细**必须作为附件上传用友**。

- 固定列：`日期 ｜ 星期 ｜ 假期/调休（含节日名）｜ 是否加班 ｜ 补助天数（0.5/1）｜ 说明`，**每天一行**，尾部加合计行与「待确认」清单；
- 命名 `02-补助逐日台账-<区间>.txt`，放在补助行 `☆附件/` 下，位于汇率截图之后；
- 中文列宽按**显示宽度**对齐（汉字算 2 宽），否则记事本里会参差不齐。

**③ 顺带勘误**

`报销单填写逻辑.md` 中滴滴备注示例的时间 `08:33` 有误（那是支付时间），已改为行程单「上车时间」列 `08:36`，并注明时间取值口径。

**本次实战校准**：0920~0930 批次，生成 `02-补助逐日台账-0920to0930.txt`，列出 3 天待确认加班（09-25 中秋、09-26、09-27）。

## v1.4.2 · 2026-10-04

**变更类型**：修订号（把一条软要求升级为硬性卡点）

**改了什么**

**① 反向报价的汇率：反算逻辑保留，但结果必须二次确认**

> **反算逻辑保留可用，但反算值一律不得直接用于折算与归档。**

执行顺序固定为三步：

1. 在台账汇率映射表中列出**截图原文 + 完整换算过程**（如「1 HKD = 0.1274 USD」→ `1 ÷ 0.1274 = 7.8472 → 7.85`）；
2. **停下来找用户二次确认**，或干脆请用户补一张**直接报价**截图（`1 外币 = X HKD`）；
3. 用户书面确认后，方可用于折算与归档。

**② 为什么加这条**（实战由来）

本次补助行 USD 汇率，初版用反向截图反算得 7.8472，虽然最终数值正确，但**反算本身引入了猜测成分**（四舍五入页显值、图表读数精度等）。用户随即补来直接报价截图「1 USD = 7.85 HKD」——数值吻合，反算得到验证。结论：**反算可以自证，但必须由用户来点头**，不能由我默认通过。

**③ 给用户的省事建议（写进 README）**

截图时直接搜 `USD to HKD` 即可拿到正面报价，无需反算。

**④ 涉及文件**：`SKILL.md`（第 2 步核验必含项）、`references/账单分类与勾稽规则.md`（汇率节新增硬性条款）、`references/文件识别规则.md`（汇率截图节）、`README.md`（第五节升为「七件事」，新增第 3 项）。

## v1.4.1 · 2026-10-04

**变更类型**：修订号（局部纠错 + 补充口径，无结构性变化）

**改了什么**

**① 汇率截图新增「反向报价」处理**

截图可能写成「1 HKD = X 外币」而非「1 外币 = X HKD」，**必须取倒数换算**。

- 实战案例：美元截图显示「1 Hong Kong Dollar equals 0.13 United States Dollar」→ ；
- 页面大字为四舍五入值（0.13）时，改**读走势图最后一个数据点**，用相邻两条刻度线的像素位置做线性映射（精度达 0.0001）；
- 换算过程须写进台账汇率映射表供用户确认，**禁止把反向数值直接当汇率**。

**② 明确滴滴电子发票的金额口径**

> 滴滴电子发票的「价税合计」**= 行程单金额，仍不含高速费**。

四件套金额关系（2026-10-04 实测）：

| 文件 | 金额 |
|---|---|
| 滴滴出行行程报销单 | 57.50（仅车费） |
| 滴滴电子发票「价税合计」 | 57.50（仍不含高速费） |
| 费用说明页 | 高速路桥费 9.00 |
| 支付截图 | **66.50 = 57.50 + 9.00** |

高速费**无票**，凭费用说明页佐证并入本行金额；**禁止**因「发票只开到 57.50」就把实报金额写成 57.50。

**③ 勘误提示：Grab 对账单的「上车点/下车点」两列极易读反**

实战案例：09-23 21:06 那笔实际是 ，初版误记为反向，导致被误判为「异常时段私人行程」。**读 Grab 明细时必须逐列确认 Pick-up / Drop-off 表头**，不要凭「早上往职场、晚上回酒店」的常识推断。

## v1.4.0 · 2026-10-04

**变更类型**：次版本更新（新增凭证类型 + 两条金额口径规则）

**改了什么**

**① 新增第 4 类受理凭证：滴滴用车**

受理范围由 5 类扩为 6 类。滴滴必备四件套：**滴滴出行行程报销单（票据本体）+ 滴滴电子发票 + 费用说明页 + 支付截图**。

**② 新规则：携程类凭证的退款处理**

> 实际报销金额以**退款后金额**为准，不是以支付金额为准。

```
实报金额 = 订单总额 − 已退款金额 = 行程单金额
```

- 支付金额只看得到首次扣款，**退款信息只在携程订单详情页露出**，必须单独取到；
- 台账新增 `支付金额 / 退款金额 / 实报金额` 三列并列，备注写明算式；
- 退款凭证必须归档为附件；涉及退改签手续费时须询问用户。
- 实战验证：机票支付 ¥3,748 − 已退款 ¥177 = ¥3,571 = 行程单总计 ✓

**③ 新规则：滴滴高速费**

> 实报金额 = **行程单金额 + 高速路桥费** = 支付金额

- 滴滴行程单的「金额」列**不含高速费**，高速费单独在「费用说明」页（列名「高速路桥费(全额给司机 不参与优惠)」）；
- 只拿行程单会**少报**，必须同时取到费用说明页；
- 备注写明算式，如「行程单57.5+高速费9=66.5」。
- 实战验证：行程单 ¥57.50 + 高速费 ¥9.00 = 支付 ¥66.50 ✓
